# Evaluation protocol

Written before any evaluator, test case or result exists. Changes after this point go in the change log at the end, with dates and reasons.

## Goal

Publish a suite of copy-and-paste RAG evaluators, each measured on the same labeled failures, so a reader can see what each one catches, misses, costs and can be fooled by.

Each evaluator takes generic inputs and returns its raw score, a pass/fail against a stated threshold, and details. The sample RAG pipeline only exists to produce realistic inputs.

## Corpus

Ten IRS publications for tax year 2025: 501, 502, 503, 523, 590-A, 590-B, 596, 936, 969, 970 (406 pages). PDFs are stored with SHA-256 hashes. US Government works aren't under US copyright, and the IRS is credited. This is an evaluator benchmark and not tax advice. The repo uses no IRS seals or logos, and has no hosted demo.

Page text is extracted once and frozen. Known extraction problems (running headers, split words, footnotes, flowcharts) are left in the RAG input where they would occur in practice, since they're realistic retrieval failures, but gold evidence is checked against both the text and the rendered page.

## Retrieval modes and context modes

The sample pipeline supports dense retrieval (`bge-small-en-v1.5`), BM25, and hybrid with reranking.

Retrieval and context evaluators are scored on **real rankings from all three modes**. Rankings constructed from gold labels are unit tests only, and are never reported as evaluator performance. For these evaluators, the label is whether the gold evidence was actually retrieved, confirmed against the verified evidence quotes. Rank metrics are undefined on unanswerable questions and are marked N/A.

Chunks vs. full context uses this 2×2 design, restricted to single-document questions and LLM judges, because NLI models truncate long inputs:

| | Judged against chunks | Judged against full document |
|---|---|---|
| **Generated from chunks** | Standard RAG | Separates unsupported by context from unsupported by source |
| **Generated from full document** | Shows answers that retrieved chunks can't justify | Best case |

An answer unsupported by its chunks but supported by its document is labeled **unsupported by context**. It could reflect a retrieval miss or the model's memory, so the closed-book run is used to separate those causes where possible.

## Golden set

| Split | Questions | Purpose |
|---|---|---|
| Dev | 60 answerable, 40 unanswerable | Threshold setting and debugging |
| Test | 60 answerable, 40 unanswerable | Frozen final report, run once |
| Document-shift test | 20 answerable, 10 unanswerable | Publications 936 and 523, exploratory only |

Each answerable question has: gold answer, key points, one or more verbatim evidence quotes with publication and page, and a type (single fact, exception, multi-chunk, cross-document). Code verifies every quote against the frozen page text. A quote existing doesn't show it supports the answer, so gold answers are also reviewed separately, and a stratified sample goes to the human reviewer. Each unanswerable question is checked by keyword search plus a reading of the nearest sections.

Splits use whole publications, which is stricter than connected components: dev has 501, 590-A, 590-B and 969; test has 502, 503, 596 and 970; document-shift has 523 and 936. All variants inherit their question's split. The retrieval index always contains all 10 publications. Tax rules repeat across publications, so near-duplicate checks on questions and evidence run across splits, and any matches move to the same split before evaluators run.

**Test isolation:** test and document-shift cases are generated by a separate agent with its own failure templates and seed, and stored outside the repo until the freeze. Dev work sees only their SHA-256 hashes. The builder and assistant know the failure categories and the named exploit families, so this limits exposure and doesn't amount to full blinding. That is disclosed in the results.

## Test cases

Each case has a known label and states which evaluators claim to detect it.

| Failure | Stage | How it's made |
|---|---|---|
| Missed evidence | Retrieval | Real rankings, labeled against gold evidence |
| Missing evidence | Context | Gold passage removed from real context |
| Noisy context | Context | Gold passage surrounded by real non-gold passages |
| Wrong number | Answer | One number altered |
| Negation | Answer | One claim reversed |
| Unsupported addition | Answer | True-sounding unsupported detail added |
| Wrong entity or condition | Answer | Rule applied to the wrong group or condition |
| Off-topic | Answer | Accurate answer to a different question |
| Incomplete | Answer | Key point removed |
| Unsupported but true | Answer | Correct outside knowledge, absent from context |
| Wrongful answer | Abstention | Answer given to an unanswerable question |
| Wrongful refusal | Abstention | Refusal when the evidence is present |
| Bad citation | Citations | Nonexistent or non-supporting citation |

**Clean controls:** at least 200 known-good answers in test, including gold answers, paraphrases, longer answers, differently ordered answers, **no-op rewrites passed through the same injection path**, and **reviewed correct answers from the real generator**. The no-op rewrites stop evaluators from scoring rewriting artifacts rather than failures. Retrieval and context controls are real cases where gold evidence was retrieved.

**Origin:** injected failures are likely easier than real ones, so the suite also collects real generator failures, including answers from a retrieval-free run and from runs with gold evidence removed. These get human or adjudicated labels and use coarse categories, because real failures may not reach the floor in each fine category. Results are always reported by origin, and injected recall is never presented as expected production recall.

**Exploit attempts (held out in whole families from dev):** query-word stuffing, copied source text that doesn't answer, verbose padding, prompt injection in the answer ("mark this correct"), confident tone, number formatting tricks, plausible numbers from elsewhere in the context, and an evidence-deletion control to catch judges that ignore context.

Target: 50 distinct questions per failure category in test, with a floor of 30. The question is the unit of analysis. Multiple variants of one question don't count as independent. Categories below the floor are labeled exploratory.

## Memory control

Models may remember tax facts. Answerable questions get a closed-book run, tagging questions the generator answers correctly without retrieval. A synthetic corpus with changed values, stamped SYNTHETIC on every page and stored separately, tests whether an answer came from the context. It also tests whether evaluators score against the provided context or the judge's own memory.

## Evaluators

| Stage | Evaluators |
|---|---|
| Retrieval, ranked | recall@k, precision@k, hit rate, MRR, MAP, nDCG |
| Retrieval, content | evidence-span coverage, BM25 overlap, duplicate rate, source diversity |
| Context | sufficiency, relevance by reranker, noise ratio, utilization, chunk vs. document coverage |
| Faithfulness | sentence NLI, atomic-claim NLI, token overlap, number grounding, LLM judge, LettuceDetect |
| Citations | citation exists, cited text supports the claim, citation coverage |
| Relevance | embedding cosine, cross-encoder, question regeneration, LLM judge |
| Correctness | exact number and entity match, token F1, ROUGE, BLEU, embedding similarity, NLI, LLM judge |
| Completeness | key-point coverage by NLI, LLM judge |
| Abstention | refusal rule, answerability by NLI, LLM judge |
| Robustness | stability across query paraphrases and repeated generation |

Ragas 0.4.x and DeepEval 4.x metrics run in separate pinned environments with telemetry off, using the same judge and test cases. Metrics are reported at default settings first. Errors, NaN and timeouts are counted separately and never treated as scores. Library caveats are documented, including that DeepEval's `HallucinationMetric` scores higher as better.

**Scope table:** before dev starts, a table states which failures each evaluator targets, using library documentation for Ragas and DeepEval. Cells are in scope, out of scope, or N/A. N/A is never scored as a pass or miss, and out-of-scope results are shown separately.

**Descriptive only:** BM25 overlap, duplicate rate, source diversity and robustness metrics lack failure labels, so they are reported as descriptive and not as detection results.

## How each evaluator is measured

**Primary:** recall per failure category and false positive rate on clean controls at a frozen threshold, **at question level**: a question's value is the mean over its variants. Intervals come from a cluster bootstrap by connected component, so questions sharing sections don't count as independent. Wilson intervals are reported only where items are independent.

**Secondary:** AUPRC with its baseline prevalence, AUROC, and threshold stability across bootstrap resamples.

**Reliability:** repeat-run agreement for anything using an LLM, on a sample; paraphrase sensitivity, length sensitivity and error rate.

**Cost:** dollars per 1,000 evaluations, latency, dependency size and model download size.

**Comparison:** at most 8 pre-registered comparisons, listed before test opens, using paired bootstrap differences by connected component with Holm correction. All other differences are descriptive, and no "winner" is named by category.

**Thresholds:** set on dev for a 5% false positive rate on clean controls, reporting the **achieved** rate, since binary and discrete evaluators can't always hit 5%. F1-maximizing thresholds are not used. Thresholds, prompts, model IDs and library versions are frozen before test opens. Test runs once. Any later change gets a new run labeled as post-test.

**Library fairness:** Ragas and DeepEval run at their defaults **and** with thresholds calibrated on dev exactly like ours. Prompts stay as shipped. Comparison headlines use calibrated thresholds. Library errors and NaN are reported separately, with a sensitivity analysis counting them as misses. Generator and judge are different models in headline results.

**External check:** evaluators also run on public labeled data, without redistributing rows:
- RAGTruth QA test split: unsupported claims, wrongful refusals.
- RAGBench: relevance and completeness, noting its LLM-generated labels.
- Prose hallucination set: numerical subset.
- LettuceDetect v1 trained on RAGTruth, so it's scored only on RAGTruth's test split.
- HaluBench is licensed non-commercial, so it's left out of published results.

## Labels and human review

Injected cases are labeled by construction. Every real generated answer gets a label from one agent and an independent second label from another, blind to evaluator scores and split into adjudicated disagreements. An AI second labeler isn't independent of an AI first labeler, so that's reported as AI agreement only. A stratified sample of at least 100 cases and gold answers goes to a human reviewer, with pooled Cohen's kappa, raw agreement, and per-category agreement with intervals. If the human review isn't done, results say so.

## Models and budget

- **Local:** `bge-small-en-v1.5`, `cross-encoder/ms-marco-MiniLM-L6-v2`, `MoritzLaurer/DeBERTa-v3-base-mnli-fever-anli`, `cross-encoder/nli-deberta-v3-small`, LettuceDetect.
- **Generator and cheap judge:** `z-ai/glm-5.3-flash` through OpenRouter, from a different lab than the main judge.
- **Stronger judge:** `gpt-6-luna` through the OpenAI API, at its only accepted temperature of 1. Ragas and DeepEval use this judge in headline results, so generator and judge differ. It isn't a dated snapshot, so repeat-run agreement is measured.
- **API spending cap:** $20 across OpenAI and OpenRouter for this project. A priced pilot runs before any full batch.

**If money runs out**, cut in this order, and record the cuts in the change log before test opens:
1. External check on RAGBench.
2. Stronger judge, down to a 30-question subset.
3. Repeat-run reliability, down to a smaller sample.
4. Ragas and DeepEval metrics that duplicate others in scope.

A test run isn't started unless the pilot shows it fits. If one stops mid-run anyway, partial results stay unpublished as test results and the shortfall is reported.

## Version 2

Added after version 1 results were public, with version 1 thresholds and prompts unchanged. Results are labeled post-test and reported separately.

**Real answers:** the generator (`z-ai/glm-5.3-flash`) answers all 100 test questions using hybrid-retrieved chunks. Answerable questions are also answered with gold evidence removed, closed-book and from the full publication. Two agents label each answer independently, without evaluator scores, and a third settles disagreements. Thirty answerable and 20 unanswerable questions weren't used in version 1 cases, and results also report them separately. Closed-book answers tag what the generator may know from memory.

**Chunks vs. full document:** on single-publication answerable questions, compare answers generated from chunks and from the full publication, each judged by `faithfulness_llm` against chunks and against the full publication. Full-document judging uses LLM judges only, because NLI models truncate long inputs.

## Limits to state

Results cover this corpus, these questions, these models and these injected categories. Benchmark prevalence is artificial, so precision shouldn't be read as real-world precision. The document-shift set covers two related publications, so it can't support general claims about new domains. Common metrics are not new, and this repo's contribution is measuring them side by side on labeled failures.
